34.0 Purpose
Section 34 strengthens the v11.3 rule:
Sanitize before insert.
It defines the governance boundary between raw telemetry, sanitized
orchestration memory, quarantined uncertain payloads, and referenced artifacts.
34.1 Two-pass sanitization pipeline [v11.5, amended by v11.5.1]
Before any payload enters PostgreSQL, it must pass sanitization.
The sanitization pipeline must use at least two passes:
Pass 1 — Deterministic regex redaction:
AWS access key IDs
GitHub tokens
JWT/Bearer tokens
OpenSSH private key headers
Slack tokens
generic Authorization headers
API key query parameters
password query parameters
session cookies where feasible
Pass 2 — Shannon entropy detection:
Scan alphanumeric and base64-like tokens longer than 16 characters.
Calculate Shannon entropy.
If entropy exceeds the configured threshold, treat the token as a
potential secret.
Default entropy threshold:
4.5
High-entropy handling policy:
Unknown high-entropy tokens must be redacted or quarantined.
Known non-secret high-entropy artifacts may be preserved if explicitly
allowlisted.
Allowlisted high-entropy artifact classes:
sha256 hashes
sha1 hashes
md5 hashes when explicitly marked as IOC hashes
UUIDs
request_id values
adapter_sha256 values
payload_sha256 values
model checksums
case IDs generated by the orchestrator
Context-sensitive rule:
A 64-character hex string in an IOC hash field may be preserved.
The same 64-character hex string in an unstructured log message may be
quarantined or redacted if not explicitly identified as an IOC.
Field-aware high-entropy command-line handling [v11.5.1]:
Shannon entropy detection must be field-aware.
High-entropy tokens found in analytical fields such as:
process.args
process.command_line
powershell.encoded_command
script.block
bash.command
shell.args
file.contents where explicitly used for detection
must not be blindly replaced with inline redaction if doing so would
destroy triage value.
Preferred handling:
1. Preserve the sanitized alert metadata in PostgreSQL.
2. Store the high-entropy raw artifact out-of-band using payload_ref.
3. Record sanitization_action = 'quarantine_ref'.
4. Record quarantine_reason = 'high_entropy_analytical_payload'.
Allowed sanitization_action values:
preserve_allowlisted
redact_inline
quarantine_ref
reject
Example:
A base64-encoded PowerShell argument may have high Shannon entropy, but it
may also be the primary evidence needed for triage.
The sanitizer should therefore quarantine the raw artifact by reference
rather than destroying it inline.
Inline redaction remains appropriate for:
API keys
bearer tokens
passwords
session cookies
private key headers
cloud credentials
Quarantine-by-reference is preferred for:
encoded commands
obfuscated shell arguments
suspicious script blocks
high-entropy file snippets
packed or encoded payloads where analysis value is high
Sanitization metadata must record:
sanitizer_version
regex_redaction_count
entropy_redaction_count
sanitization_action
quarantine_reason
redaction_manifest_sha256
payload_sanitization_status
34.2 Quarantine
If sanitization cannot be performed safely, or if a payload contains ambiguous
high-risk content, the payload must be quarantined.
Quarantined payloads must not be inserted into orchestration memory as normal
JSONB payload.
Allowed quarantine patterns:
Store only sanitized metadata and payload_sha256.
Store payload_ref to an out-of-band artifact store.
Store a redacted summary only.
Reject the payload and log the rejection.
Quarantine reasons must be recorded.
34.3 payload_ref governance
payload_ref artifacts must be content-addressed or otherwise integrity-checked.
Each payload_ref must include:
canonical URI,
sha256,
size_bytes,
compression,
sanitizer_version,
sanitization_status,
sanitization_action,
retention_class.
payload_ref artifacts must not be treated as trusted input. They remain subject
to the same untrusted payload discipline as inline JSONB payloads.
34.4 Retention and deletion
Sanitized orchestration memory follows Section 30 retention rules.
Referenced artifacts must have explicit retention classes.
Retention classes should distinguish:
short-term operational artifacts,
90-day IOC-related artifacts,
long-term audit artifacts,
training/correction-derived artifacts,
quarantined artifacts,
externalized Wiki artifacts [v11.6].
Deletion or archive must be auditable.
34.5 Acceptance criteria
Known secret patterns are redacted or blocked in CI tests.
High-entropy unknown tokens are redacted or quarantined.
Approved high-entropy artifact classes are preserved when explicitly
expected.
High-value suspicious command-line payloads are quarantined by reference
where inline redaction would destroy analytical value.
Quarantine path is tested.
payload_ref integrity check passes.
Sanitization metadata is present in relevant ledger rows.
Raw unsanitized telemetry is not present in PostgreSQL.
Retention classes are documented.
Generated Wiki Markdown is sanitized before commit when Wiki generation is
enabled.
